# VELFORT — Threat Model

Статус: **ревизия 2 (после [ARCHITECTURE_REVIEW.md](ARCHITECTURE_REVIEW.md)), ожидает утверждения**. Методика: перечисление активов и границ доверия,
затем угрозы по сценариям (с опорой на категории STRIDE). Каждая угроза содержит: сценарий, последствия,
механизм защиты, остаточный риск, способ проверки. Ссылки `SR-*` ведут в
[SECURITY_REQUIREMENTS.md](SECURITY_REQUIREMENTS.md).

> VELFORT **не защищает** от вредоносного ПО, работающего с правами пользователя или администратора
> в момент, когда хранилище разблокировано или пароль вводится. Это ограничение любого локального
> менеджера паролей и указывается явно.

## 1. Активы

| Актив | Ценность |
|---|---|
| A1. Master Password | Даёт доступ ко всему хранилищу и всем бэкапам |
| A2. DEK и подключи | Эквивалентны доступу ко всем данным текущего и прошлых файлов |
| A3. Секреты записей | Пароли, карты, ключи, TOTP |
| A4. Метаданные записей | Какими сервисами пользуется человек, личные данные |
| A5. Целостность хранилища | Пользователь должен видеть свои настоящие данные |
| A6. Доступность | Потеря хранилища = потеря всех паролей |

## 2. Границы доверия

1. **Диск** (файл хранилища, бэкап, конфиг) — недоверенный: может быть прочитан, скопирован, изменён.
2. **WebView2 / JS** — недоверенная зона отображения (возможен XSS через содержимое записей, ошибки зависимостей).
3. **Импортируемые файлы** — враждебный вход.
4. **ОС и другие процессы пользователя** — частично доверенные: VELFORT опирается на ядро ОС, но не доверяет
   буферу обмена и другим приложениям.
5. **Цепочка поставки** (crates, npm, toolchain) — частично доверенная, контролируется.

## 3. Атакующие

| ID | Атакующий | Возможности |
|---|---|---|
| ATK-1 | Offline: вор ноутбука, доступ к копии файла/бэкапа/облачной папке | Неограниченное время, GPU/ASIC для перебора |
| ATK-2 | Активный с доступом на запись к файлам (без исполнения кода при открытом хранилище) | Подмена, откат, порча файлов |
| ATK-3 | Вредоносное ПО с правами пользователя | Чтение памяти, кейлоггинг, скриншоты, буфер обмена |
| ATK-4 | Злоумышленник через содержимое (импорт, вставленный текст, URL в записи) | Попытки XSS/инъекций, DoS парсера |
| ATK-5 | Компрометация зависимости/сборки | Произвольный код в приложении |

## 4. Угрозы

### T-01. Кража компьютера (выключен или заблокирован)
1. **Сценарий:** ATK-1 получает диск, копирует `.velfort`.
2. **Последствия:** при слабом Master Password — раскрытие всех данных.
3. **Защита:** все секреты и метаданные под AEAD (SR-ENC-*); ключ только из Argon2id с высокими параметрами
   (SR-KDF-*); блокировка перед сном (SR-LOCK-4); рекомендация BitLocker в onboarding.
4. **Остаточный риск:** слабый пароль перебирается; если ноутбук украден в состоянии сна **с открытым
   хранилищем** до срабатывания блокировки — ключ в RAM (cold boot/DMA).
5. **Проверка:** тест-сканер «нет открытых данных в файле» с сигнальными строками (SR-TEST-1); тест
   блокировки по `PBT_APMSUSPEND` на Windows (e2e/ручной протокол).

### T-02. Копирование файла базы данных
1. **Сценарий:** файл синхронизируется в облако или копируется вредоносом/коллегой.
2. **Последствия:** offline-перебор (см. T-04), анализ метаданных.
3. **Защита:** как T-01; минимизация открытых метаданных (DATA_MODEL §2); padding.
4. **Остаточный риск:** видны число записей, число ревизий, приблизительные размеры, vault_id.
5. **Проверка:** SR-TEST-1; ревью таблицы классификации данных.

### T-03. Доступ к резервной копии
1. **Сценарий:** ATK-1 находит `.velfort-backup` на флешке/в облаке.
2. **Последствия:** как T-02; кроме того, бэкап может быть зашифрован **старым** паролем.
3. **Защита:** бэкап полностью зашифрован (DATA_MODEL §6), содержит копию заголовка с теми же параметрами KDF.
4. **Остаточный риск:** старые бэкапы со старым (возможно слабым/скомпрометированным) паролем остаются
   действительными; VELFORT не может удалить их.
5. **Проверка:** сканер сигнальных строк по бэкапу; тест «бэкап после смены пароля открывается старым паролем
   и не открывается новым» (документирует поведение).

### T-04. Подбор Master Password
1. **Сценарий (offline):** перебор по словарям с GPU по скопированному заголовку.
   **Сценарий (online):** перебор через UI на разблокированном ПК.
2. **Последствия:** полное раскрытие.
3. **Защита:** Argon2id с калибровкой (≥ 64 MiB, t=3, p=4); требования к силе пароля при создании
   (минимальная оценочная энтропия, предупреждения); генерация парольной фразы как рекомендованный путь;
   UI-backoff для online-сценария.
4. **Остаточный риск:** Argon2id лишь замедляет перебор; пароль с низкой энтропией не защищён. Backoff в UI
   не защищает от ATK-1.
5. **Проверка:** тест, что параметры ниже минимума отвергаются при создании и при открытии; бенчмарк
   времени unlock; тест неверного пароля (SR-TEST-3).

### T-05. Повреждение базы данных
1. **Сценарий:** сбой питания, ошибка диска, неудачная синхронизация, обрыв записи.
2. **Последствия:** потеря доступа ко всем или части данных.
3. **Защита:** транзакции SQLite с `synchronous=FULL`; атомарная смена заголовка; `PRAGMA integrity_check`
   при открытии (опционально по времени); защитная копия файла перед миграцией/rekey (CRYPTOGRAPHY §7.5); восстановление только в новый файл;
   изоляция повреждённой записи (остальные доступны).
4. **Остаточный риск:** повреждение без свежего бэкапа = потеря данных. Пользователь отвечает за хранение
   внешних бэкапов; приложение напоминает.
5. **Проверка:** fuzz/мутационные тесты файла (случайные байты, усечение) — приложение не паникует и не
   возвращает частичные/неверные данные (SR-TEST-4); тест прерывания транзакции.

### T-06. Подмена зашифрованных данных
1. **Сценарий:** ATK-2 меняет байты шифротекста, переставляет blob'ы между записями, удаляет строку,
   откатывает строку или весь файл, понижает параметры KDF в заголовке.
2. **Последствия:** пользователь видит неверные данные (например, старый пароль), DoS, ослабление KDF.
3. **Защита:** AEAD (любое изменение → отказ); AAD с vault_id/**purpose**/id/revision (перестановка между записями,
   между summary↔payload, history→current → отказ; CRYPTOGRAPHY §4); заголовок в AAD обёртки DEK (понижение
   параметров → отказ); манифест с `header_hash` (удаление, добавление, откат строки, откат заголовка → предупреждение;
   CRYPTOGRAPHY §5.1); `last_seen_generation` с HMAC под `K_local` в конфиге (откат файла → предупреждение, §5.3).
4. **Остаточный риск:** **откат всего файла на старое согласованное состояние по содержимому файла не обнаруживается
   — для этого нужно доверенное внешнее состояние, которого в v1 нет** (CRYPTOGRAPHY §5.2). Локальная мера не помогает,
   если атакующий возвращает и `config.json`, и при открытии на другом ПК. DoS (удаление файла) не предотвращается.
5. **Проверка:** тесты flip-бита в каждом поле envelope, перестановки summary/payload между записями,
   переноса между хранилищами, удаления строки, отката ревизии, изменения каждого поля заголовка (SR-TEST-2).

### T-07. Атаки через импортируемые файлы
1. **Сценарий:** ATK-4 подсовывает CSV/JSON «экспорт из другого менеджера» с гигантскими полями,
   глубокой вложенностью, `javascript:` URL, HTML/скриптами в заголовках, CSV-формулами.
2. **Последствия:** DoS, XSS в WebView (а через IPC — вызов команд), инъекция при последующем экспорте в CSV.
3. **Защита:** парсинг только в Rust; лимиты размера файла, числа записей, длины полей, глубины;
   строгие схемы; предпросмотр перед записью; React рендерит текст без `dangerouslySetInnerHTML` (запрет
   линтером); URL открываются только `https`/`http` после подтверждения; при экспорте CSV — экранирование
   ведущих `= + - @`; CSP без `unsafe-inline` для скриптов.
4. **Остаточный риск:** ошибки в парсерах; социальная инженерия.
5. **Проверка:** fuzz-тесты парсеров (`cargo fuzz`), набор вредоносных фикстур (SR-TEST-7), e2e-тест
   с XSS-полезными нагрузками в полях записи.

### T-08. Вредоносное ПО с правами пользователя
1. **Сценарий:** ATK-3 запущен в сеансе пользователя.
2. **Последствия:** при открытом хранилище или при вводе пароля — полное раскрытие; может подменить сам
   `VELFORT.exe` или внедриться в процесс.
3. **Защита:** **принципиально ограничена.** Меры, повышающие стоимость: установка per-machine в Program Files
   (запись требует администратора; NSIS Tauri по умолчанию ставит per-user в `%LOCALAPPDATA%` — поэтому требуется
   `installMode: perMachine`, SR-DIST-1), подпись бинарника (при наличии сертификата), короткое время открытия,
   автоблокировка, копирование без передачи в JS, исключение из истории буфера.
4. **Остаточный риск:** высокий. Явно заявляется: VELFORT не защищает от скомпрометированной ОС/сеанса.
5. **Проверка:** документирование; ревью, что в документации и UI нет обратных обещаний.

### T-09. Кейлоггеры
1. **Сценарий:** перехват ввода Master Password.
2. **Последствия:** ATK получает пароль; вместе с копией файла — полный доступ.
3. **Защита:** ограничена. Второй фактор (Secret Key / key file) **отложен решением владельца**; в v1 перехваченного пароля и копии файла
   достаточно для доступа. Иерархия ключей оставляет точку расширения (CRYPTOGRAPHY §2). Ввод пароля только в окне VELFORT.
4. **Остаточный риск:** высокий при наличии кейлоггера с доступом к файлам.
5. **Проверка:** документирование; при реализации второго фактора — тест «пароль без ключа не открывает».

### T-10. Чтение памяти процесса
1. **Сценарий:** ATK-3 (`ReadProcessMemory`), дамп процесса, pagefile, hiberfil, crash dump.
2. **Последствия:** извлечение DEK/секретов.
3. **Защита:** минимизация времени жизни, `zeroize`, `VirtualLock` для ключей, опционально
   `CryptProtectMemory(SAME_PROCESS)`, блокировка при сне, без crash-reporter'ов.
4. **Остаточный риск:** процесс того же пользователя может читать память VELFORT; гибернация и полные
   дампы памяти документацией `VirtualLock` не покрыты; копии значений, созданные Rust/аллокатором или
   WebView2, не контролируются полностью.
5. **Проверка:** тест в Windows: дамп процесса после блокировки (procdump) и поиск сигнальных значений;
   ожидаемый результат — DEK и пароли отсутствуют после блокировки (best effort; результат фиксируется в отчёте).

### T-11. Секреты и Master Password в WebView / JS
1. **Сценарий:** (a) Master Password, введённый в React-поле, остаётся строкой в renderer-процессе WebView2 и в
   IPC-буферах; (b) раскрытый пароль записи остаётся в JS-куче, DOM, undo-истории, user data folder WebView2;
   (c) XSS или скомпрометированная npm-зависимость читает поле Master Password при вводе.
2. **Последствия:** утечка Master Password даёт доступ к будущим сессиям и ко всем бэкапам; утечка отдельных секретов.
3. **Защита (v1, ARCHITECTURE_REVIEW §3.1, вариант A):** неуправляемое поле без React state, очистка
   `input.value` сразу после отправки, перезагрузка документа после unlock/lock; секреты записей — только по
   `item_reveal_field` с таймером; копирование без передачи в JS; запрет хранения данных записей в
   `localStorage`/`IndexedDB`; отключение PasswordAutosave/autofill WebView2 (проверить W6); CSP, isolation,
   отсутствие сетевых плагинов для ограничения каналов эксфильтрации.
4. **Остаточный риск:** **Master Password в v1 проходит через JavaScript**; строки JS и IPC-буферы не затираются
   гарантированно; скомпрометированный frontend может перехватить Master Password при вводе (и, в открытом
   сеансе, запросить любые секреты через IPC). Нативный ввод (вариант C) — исследование Phase 0.5 (W9).
5. **Проверка:** e2e: после unlock/lock в DOM и JS-состоянии нет значений; сканер сигнальных строк по UDF WebView2;
   дамп процесса WebView2 после lock (W13, best effort, результат фиксируется как есть); ESLint-правила.

### T-12. Перехват буфера обмена
1. **Сценарий:** другое приложение/менеджер буфера читает скопированный пароль; Windows Clipboard History / Cloud Clipboard.
2. **Последствия:** раскрытие отдельных секретов.
3. **Защита:** формат `ExcludeClipboardContentFromMonitorProcessing` и др. через `arboard`; автоочистка
   через N секунд, только если значение наше; очистка при блокировке.
4. **Остаточный риск:** любое приложение может прочитать буфер в окне времени; сторонние менеджеры буфера
   могут игнорировать флаги. **Удаление из буфера не гарантируется.**
5. **Проверка:** интеграционный тест на Windows: после копирования запись отсутствует в истории
   (`Win+V`, ручной протокол) и буфер очищается по таймеру; тест «не очищаем чужое содержимое».

### T-13. Компрометация зависимостей и сборки
1. **Сценарий:** вредоносная версия crate/npm-пакета, typosquatting, скомпрометированный CI.
2. **Последствия:** произвольный код с доступом к расшифрованным данным.
3. **Защита:** минимум зависимостей (обоснование каждой в PR); lock-файлы; `cargo-deny` + `cargo-audit` +
   `npm audit` в CI; запрет git/неофициальных источников; Dependabot-обновления с ревью;
   ограниченные права CI-токенов; воспроизводимость сборки (цель).
4. **Остаточный риск:** атака на легитимного мейнтейнера популярной зависимости.
5. **Проверка:** CI-проверки обязательны для merge; периодический ручной аудит `cargo tree`/`npm ls`.

### T-14. Ошибки реализации криптографии
1. **Сценарий:** повтор nonce, отсутствие AAD, использование неверного ключа, ошибочная проверка тега,
   утечка через логи/ошибки, неверная обработка Unicode в пароле.
2. **Последствия:** от частичной до полной потери конфиденциальности/целостности.
3. **Защита:** только библиотечные примитивы; централизованный `crypto`-модуль с минимальным API
   (нельзя зашифровать без AAD; nonce генерируется внутри); типы ключей разных классов не взаимозаменяемы;
   NFC-нормализация пароля; ревью каждого изменения `crypto`; известные тестовые векторы (RFC 9106, XChaCha draft).
4. **Остаточный риск:** логические ошибки, не покрытые тестами; рекомендуется **внешний аудит** до 1.0.
5. **Проверка:** тестовые векторы; property-тесты (encrypt/decrypt, неуникальность nonce в 10^6 вызовах);
   негативные тесты (SR-TEST-2); `cargo-mutants` для модуля crypto (оценить).

### T-15. Подмена исполняемого файла / DLL hijacking
1. **Сценарий:** поддельный `VELFORT.exe` или подложенная DLL рядом с бинарником собирают Master Password.
2. **Последствия:** раскрытие пароля.
3. **Защита:** установка per-machine в Program Files (SR-DIST-1); подпись Authenticode (обязательна до публичного релиза); проверка подписи
   установщиком; использование безопасного порядка поиска DLL (оценить `SetDefaultDllDirectories`).
4. **Остаточный риск:** пользователь может запустить фишинговую копию.
5. **Проверка:** проверка подписи релиза в CI; ревью настроек загрузки DLL.

### T-16. Атаки на резервные копии и восстановление
1. **Сценарий:** подмена/усечение/перестановка сегментов бэкапа; подсовывание вредоносного «бэкапа» (огромный
   заголовок, экстремальные параметры KDF, не-SQLite содержимое); сбой во время восстановления.
2. **Последствия:** восстановление неверных данных, DoS, повреждение существующего хранилища.
3. **Защита:** STREAM (`aead-stream` `StreamBE32`) с AAD = hash заголовка; лимиты заголовка и KDF; полная проверка в
   памяти до записи (CRYPTOGRAPHY §7.4); восстановление только в новый файл; без временных расшифрованных файлов.
4. **Остаточный риск:** атомарность `MoveFileExW` документацией Microsoft не заявлена; внешний аудит `aead-stream`
   не найден.
5. **Проверка:** SR-TEST-6, SR-BAK-*; W12 (kill процесса во время восстановления).

### T-17. Повтор nonce
1. **Сценарий:** сбой CSPRNG, ошибка API, клонирование ВМ со снимком состояния RNG.
2. **Последствия:** при повторе (ключ, nonce) для XChaCha20-Poly1305 — раскрытие XOR открытых текстов и возможность
   подделки.
3. **Защита:** nonce генерируется только внутри `crypto::seal`; ошибка `getrandom` прерывает операцию; отдельные ключи
   по классам данных и для каждого потока бэкапа (CRYPTOGRAPHY §3).
4. **Остаточный риск:** клонирование ВМ — проблема уровня ОС; вероятность случайной коллизии ≤ 2^-129 при 2^32
   шифрованиях одним ключом.
5. **Проверка:** ревью API (nonce не принимается извне); property-тест уникальности; тест реакции на ошибку RNG
   (внедрение отказа через тестовый источник случайности только в `cfg(test)`).

## 5. Угрозы вне области защиты (явно)

* Вредоносное ПО/администратор, контролирующие систему во время ввода пароля или работы с открытым хранилищем.
* Аппаратные атаки (cold boot, DMA, аппаратные кейлоггеры) на включённую систему.
* Социальная инженерия и принуждение к раскрытию пароля.
* Откат всего файла и профиля пользователя на старое согласованное состояние.
* Безвозвратная потеря данных при отсутствии внешних бэкапов или при забытом Master Password
  (**восстановления пароля нет по построению**).
* Утечки на уровне файловой системы/SSD (теневые копии, wear leveling) уже удалённых зашифрованных страниц
  — остаются зашифрованными, но могут содержать старые ревизии под тем же DEK.
