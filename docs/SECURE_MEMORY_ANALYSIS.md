# VELFORT — Secure Memory Analysis (F-1: Argon2id working memory)

Дата: 2026-11-26. Статус F-1: **MITIGATED — решение выбрано и подтверждено измерением в Linux-контейнере и
Windows CI в пределах охвата измерителя; не FIXED** (охват измерителя неполный, физическая Windows 11 не проверялась).

## 1. Проблема

Phase 0.5 (по исходнику `argon2` 0.6.0): рабочая память Argon2id освобождается без затирания. Рабочая память и её
производные значения зависят от Master Password; их остатки в памяти процесса после разблокировки — материал для
атаки чтением памяти (THREAT_MODEL T-10) и для дампов (T-18).

## 2. Анализ исходного кода `argon2` 0.6.0

| Место | Что | Затирается? |
|---|---|---|
| `src/lib.rs:285-289` `hash_password_into` | выделяет `Blocks::new(blocks_len)` и вызывает `hash_password_into_with_memory` | — |
| `src/block.rs:166-188` `Blocks::new` | `alloc_zeroed`; при null → `None` → `Error::OutOfMemory` (без abort) | — |
| `src/block.rs:190-200` `Drop for Blocks` | **только `dealloc`** | **Нет** |
| `src/lib.rs:307-330` `hash_password_into_with_memory` | **публичный API**, память — от вызывающего (`impl AsMut<[Block]>`) | память принадлежит вызывающему |
| `src/lib.rs:383-386` | `let mut hash = [0u8; Block::SIZE]` — G(H0‖i‖l), первые блоки каждой полосы, на стеке | **Нет** |
| `src/lib.rs:389-390` | `initial_hash.zeroize()` (feature `zeroize`) | Да |
| `src/block.rs:80-114` `Block::compress` | временные `r`, `q` (1 KiB каждый) на стеке | **Нет** |
| `src/lib.rs:400-402` `address_block`, `input_block` | адреса Argon2i-части; строятся из **публичных** параметров (pass, lane, slice, m, t, тип, счётчик) | Нет (несекретно) |

Вывод: публичный API позволяет взять под контроль **кучу** (через `hash_password_into_with_memory`), но не
**стековые** временные значения внутри crate.

## 3. Рассмотренные варианты

| # | Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|---|
| 1 | Собственный буфер `Vec<Block>` + затирание через `Zeroize` для `Block` (feature `zeroize`), обёртка `WipeOnDrop` | Публичный API; без `unsafe`; затирание на `Ok`, `Err` и при раскрутке паники | Не покрывает стек | **Принят** |
| 2 | Очистка стека: `#[inline(never)] fn scrub_stack()` с массивом 256 KiB + `zeroize` сразу после KDF в том же кадре | Без `unsafe`; измеримо устраняет найденные копии tag | Best-effort: зависит от раскладки кадров и оптимизаций; не гарантия | **Принят как дополнение** |
| 3 | KDF в отдельном потоке (стек 2 MiB), очистка стека внутри потока | Те же результаты, что 1+2 | Не дал преимущества в измерениях | Не обязателен |
| 4 | Форк `argon2` с затиранием стека / `Drop` | Полное покрытие внутри crate | Сопровождение форка криптобиблиотеки; запрещено правилами без крайней необходимости | Отклонён |
| 5 | Другая реализация (`rust-argon2`, привязки к libsodium/libargon2) | Возможны иные гарантии затирания | Новые зависимости / C-код; исходники не исследовались в Phase 0.6 | Не исследовано — открытый вопрос |
| 6 | Только затирание выходного буфера | — | **Маскирует проблему** — не применяется | Отклонён |

Компиляторные оптимизации: `zeroize` 1.9.2 использует `ptr::write_volatile` и `atomic::compiler_fence`
(`src/lib.rs`, исходник проверен grep); это предназначено именно для того, чтобы запись не была удалена
оптимизатором. Ограничение `zeroize` (документация в исходнике): для `Vec` — «"Best effort" zeroization … Cannot ensure
that previous reallocations did not leave values on the heap» — у нас `Vec<Block>` выделяется один раз
`try_reserve_exact` и не реаллоцируется.

Поведение: успех — буфер затёрт; ошибка (`OutputTooShort`) — затёрт; паника при раскрутке — затёрт (тесты
`work_is_wiped_after_success`, `work_is_wiped_after_error`, `work_is_wiped_during_unwinding`). В release VELFORT
`panic = "abort"` — раскрутки нет; процесс завершается, память возвращается ОС (затирания нет — ограничение).

## 4. Измерение остатков (`spikes/argon2-memory`)

Методика: эталонный дочерний процесс вычисляет Argon2id и сохраняет маскированные отпечатки (первые 32 байта) всех
**итоговых** блоков и итогового ключа (tag). Родитель выполняет KDF в проверяемом варианте, освобождает всё и
сканирует **собственную** читаемую память (Linux: `/proc/self/maps` + `/proc/self/mem`; Windows: `VirtualQueryEx` +
`ReadProcessMemory`), исключая адреса собственного буфера сканера. Позитивный контроль — вариант, намеренно не
освобождающий рабочую память.

| Вариант | Linux-контейнер 64 MiB (блоки / tag) | Linux 64 KiB | Windows CI 64 MiB | Windows CI 64 KiB |
|---|---|---|---|---|
| positive-control-leak | 65536 / 2 | 64 / 2 | 65536 / 8 | 64 (128 адресов) / 6 |
| lib-default (`hash_password_into`) | 0 / 2 | **61** / 2 | 0 / 8 | 0 / 2 |
| own-nozero | 0 / 2 | **61** / 2 | 0 / 6 | 0 / 2 |
| own-zeroizing | 0 / 2 | 0 / 2 | 0 / 8 | 0 / 2 |
| **own-zeroizing-scrub** | **0 / 0** | **0 / 0** | **0 / 0** | **0 / 0** |
| thread-zeroizing-scrub | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |

Интерпретация:
* Измеритель работает: позитивный контроль находит все блоки на обеих ОС.
* F-1 **воспроизведён** (Linux, 64 KiB): стандартный путь оставляет 61 из 64 блоков в освобождённой куче.
* Для 64 MiB освобождённые блоки на обеих ОС не найдены — крупная аллокация возвращается ОС (наблюдение; не
  гарантия: при иных размерах/аллокаторах поведение может отличаться, а pagefile не проверялся).
* **Копии итогового ключа (tag = материал для KEK) остаются на стеке** во всех вариантах без очистки стека
  (2–8 вхождений); очистка стека устраняет их на обеих ОС.

## 5. Выбранное решение (для Phase 1, требует утверждения)

1. Argon2id вызывается **только** через `hash_password_into_with_memory` с буфером `Vec<Block>`, выделенным
   `try_reserve_exact` (ошибка выделения → ошибка, не abort), обёрнутым `WipeOnDrop` (затирание на всех путях).
2. Сразу после KDF в том же кадре — `scrub_stack()` (256 KiB).
3. Выходной ключ — в `Zeroizing<[u8; 32]>`; HKDF-производные — в типах с `ZeroizeOnDrop`.
4. Регрессионный тест — измеритель остатков в CI (Linux и Windows) с позитивным контролем; критерий: 0 остатков
   блоков и tag в выбранном варианте.

Цена: [CI] 256 MiB/t=3/p=4 — 480 vs 444 мс (Phase 0.5; затирание 256 MiB), очистка стека — единицы мс (64 MiB: 125 vs 115 мс в одном замере).

## 6. Остаточные риски

* Измеритель видит только **итоговые** значения блоков и tag; промежуточные значения (`r`/`q`, ранние проходы,
  состояние BLAKE2b) не отпечатываются → их отсутствие **не доказано**.
* Очистка стека — best-effort; другой компилятор/уровень оптимизации может разместить кадры иначе; поэтому тест
  обязателен в CI для каждой сборки.
* Память, выгруженная в pagefile до затирания, гибернация, дампы ядра — вне охвата.
* Пароль до нормализации и строки в WebView2 (вариант A) — отдельный остаточный риск (THREAT_MODEL T-11).
* Физическая Windows 11 — не проверено (P-03).
