## 3. Обнаруженные проблемы

### 3.1. Master Password и JavaScript (уточнение владельца, §2 задания)

**Факт о текущей документации.** В документах этапа 0 не было утверждения, что Master Password не попадает
в JavaScript; напротив, CRYPTOGRAPHY.md ревизии 1, §4 (шаг 2), говорил: «Пароль поступает из WebView через IPC
команду `vault_unlock`». Однако формулировка CRYPTOGRAPHY.md ревизии 1, §7 («Значения пароля в JS появляются только
при „показать“») относилась к паролям записей и могла читаться как относящаяся к Master Password. Это
неоднозначность (**дефект D2**), исправлена.

**Сравнение вариантов**

| | A. React-поле в WebView2 (с минимизацией) | B. Системный диалог `CredUIPromptForWindowsCredentialsW` | C. Собственный нативный компонент (Win32-окно с `EDIT` + `ES_PASSWORD`) |
|---|---|---|---|
| Где существует пароль | DOM `input.value`, строки JS в renderer-процессе WebView2 (отдельный процесс, S11), буферы IPC Tauri/WebView2, затем Rust | Процесс(ы) Credential UI + буфер `ppvOutAuthBuffer` в VELFORT (S9), затем Rust | Память процесса VELFORT (буфер edit control в куче USER), затем Rust |
| Граница доверия | Пароль пересекает границу WebView → Rust; весь frontend-код и его зависимости видят пароль | Пароль не входит в WebView; доверие системному компоненту Windows | Пароль не входит в WebView; доверие нашему нативному коду |
| Угрозы | XSS/скомпрометированная npm-зависимость читает пароль; копии строк в куче V8 не затираются; копии в IPC-буферах вне контроля `zeroize` | Обучение пользователя вводить мастер-пароль в системные окна (фишинг-подобный паттерн); `CREDUIWIN_SECURE_PROMPT` (secure desktop) **несовместим** с `CREDUIWIN_GENERIC` (S9) — для произвольного пароля secure desktop недоступен | Ошибки собственного Win32-кода (unsafe FFI); буфер edit control не затирается гарантированно; возможность чтения через WM_GETTEXT из другого процесса документацией не исключена (S10) |
| Ограничения | Гарантированное затирание невозможно | Нельзя оформить в стиле VELFORT (`hbmBanner` игнорируется, только caption/message, S9); API предназначен для учётных данных Windows | Ограниченная стилизация (цвета, шрифт), ручная поддержка DPI, фокуса, IME, accessibility, тёмной/светлой тем, позиционирования над окном Tauri |
| Сложность | Низкая | Средняя | Высокая |
| Влияние на UI | Полностью фирменный экран блокировки | Чужеродный системный диалог — противоречит требованию к фирменному экрану блокировки | Экран блокировки — гибрид WebView + нативное поле; риск визуальных артефактов |
| Что реально выигрывается | — | Защита пароля от скомпрометированного frontend | То же |

**Ключевое наблюдение.** Скомпрометированный frontend (XSS, вредоносная npm-зависимость) в разблокированном
состоянии и так может вызвать `item_reveal_field` для любых записей. Варианты B/C защищают **Master Password**
(а значит, будущие сессии и бэкапы) от такого frontend, но **не содержимое хранилища** во время открытой сессии.
От вредоносного ПО с правами пользователя (кейлоггер) не защищает ни один вариант.

**Решение для v1: вариант A с обязательными мерами**, и прототип варианта C в Phase 0.5 для оценки стоимости:

1. Неуправляемое поле (`<input type="password">` через `ref`), **без** хранения в React state/store, без
   логирования, без `console`, `autocomplete="off"` (атрибут `autocomplete="new-password"` при создании),
   `spellcheck=false`.
2. При отправке: чтение `value` один раз → немедленно `input.value = ''` → `invoke('vault_unlock', …)`.
   Передача как сырого `Uint8Array` с последующим `fill(0)` — **проверить в Phase 0.5**, поддерживает ли
   используемая версия Tauri raw-тело IPC для этой команды; это уменьшает число копий, но **не устраняет**
   строку `input.value`.
3. После успешной разблокировки и после блокировки — перезагрузка документа (освобождение ссылок для GC,
   без гарантии затирания).
4. Отключение автосохранения паролей WebView2 (в UDF есть категория `PasswordAutosave`, S12) — механизм
   настройки в Tauri/wry **проверить в Phase 0.5**.
5. CSP, isolation, отсутствие сетевых плагинов — снижают каналы эксфильтрации из скомпрометированного JS;
   проверяется негативными тестами Phase 0.5.
6. В документации и UI: «Master Password вводится в интерфейсе приложения и передаётся в защищённое ядро;
   полная изоляция от интерфейсного слоя в версии 1 не обеспечивается».

## 4. Остающиеся риски

| Риск | Уровень | Комментарий |
|---|---|---|
| Master Password и раскрытые секреты в памяти WebView2 | Высокий (в рамках модели — средний) | Вариант A; затирание невозможно |

| Слабый Master Password | Высокий | Argon2id лишь замедляет перебор |

## 6. Вопросы, требующие решения владельца

1. **Master Password в v1:** принять вариант A (React-поле с мерами §3.1) с остаточным риском, а вариант C
   исследовать в Phase 0.5? Или требовать вариант C уже в v1 (заметно увеличит срок)?
2. **`journal_mode`:** DELETE (предложено) или WAL?
3. **`webviewInstallMode`:** `offlineInstaller` (~127 МБ, установка без сети, S15) или `downloadBootstrapper`
   (по умолчанию, требует интернет при установке)? Для offline-first предложен `offlineInstaller`.
4. **Восстановление поверх существующего хранилища** в v1 не поддерживается (только в новый файл) — согласны?
