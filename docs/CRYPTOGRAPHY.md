# VELFORT — Cryptography

Статус: **черновик, ожидает утверждения**. Все параметры, помеченные «калибруется», будут зафиксированы
только после измерений на целевом оборудовании.

Базовые правила:

* Никакой собственной криптографии: только примитивы из проверенных библиотек (RustCrypto).
* Все криптографические операции выполняются в Rust-процессе VELFORT. Frontend (WebView) не получает ключей
  и не выполняет шифрование.
* Каждый шифротекст — аутентифицированный (AEAD) и привязан к контексту через AAD (Associated Data).

## 1. Выбранные примитивы и обоснование

| Назначение | Примитив | Rust crate (версия на 2026-11-25, crates.io) |
|---|---|---|
| Выработка ключа из Master Password | **Argon2id** (RFC 9106) | `argon2` 0.6.0 |
| Шифрование данных и обёртка ключей | **XChaCha20-Poly1305** (AEAD, 192-битный nonce) | `chacha20poly1305` 0.11.0 |
| Разделение ключей (domain separation) | **HKDF-SHA-256** (RFC 5869) | `hkdf` 0.13.0 + `sha2` |
| Генерация случайности | CSPRNG ОС (`BCryptGenRandom`/`ProcessPrng` на Windows через `getrandom`) | `getrandom` 0.4.3 / `rand` 0.10.4 (`OsRng`) |
| Очистка памяти | `zeroize`, обёртки `secrecy` | `zeroize` 1.9.2, `secrecy` 0.10.3 |
| Сравнение в постоянное время | `subtle` | `subtle` 2.6.1 |
| TOTP (этап 5) | HMAC-SHA-1/256/512 по RFC 6238 | `totp-rs` 6.0.0 (оценить) или собственная обвязка над `hmac` — решение на этапе 5 |

Версии получены запросом к `https://crates.io/api/v1/crates/<name>` 2026-11-25 и будут зафиксированы
в `Cargo.lock`. Точная привязка к конкретному способу получения энтропии на Windows зависит от версии
`getrandom` и будет проверена по его исходному коду при внедрении.

### 1.1. Почему Argon2id

* RFC 9106, §1: «Argon2id MUST be supported by any implementation of this document» — Argon2id является
  обязательным вариантом стандарта и сочетает устойчивость к side-channel (Argon2i) и к GPU/ASIC-перебору (Argon2d).
* OWASP Password Storage Cheat Sheet рекомендует Argon2id первым выбором.
* Быстрые хеш-функции (SHA-256 и т.п.) не используются для выработки ключа из пароля (ТЗ 4.1).

### 1.2. Параметры Argon2id

Источники (проверены 2026-11-25):

* **OWASP** (https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
  минимальные конфигурации: `m=47104 (46 MiB), t=1, p=1`; `m=19456 (19 MiB), t=2, p=1`;
  `m=12288 (12 MiB), t=3, p=1`; `m=9216 (9 MiB), t=4, p=1`; `m=7168 (7 MiB), t=5, p=1`.
  Это **минимумы для серверного хранения хешей**, где сервер обрабатывает много входов одновременно.
* **RFC 9106 §4** (https://www.rfc-editor.org/rfc/rfc9106.html):
  FIRST RECOMMENDED — `t=1, p=4, m=2^21 (2 GiB)`, 128-битная соль, 256-битный тег;
  SECOND RECOMMENDED — `t=3, p=4, m=2^16 (64 MiB)`, 128-битная соль, 256-битный тег.

Для локального менеджера паролей Argon2id вычисляется **один раз при разблокировке** на машине пользователя,
поэтому разумно идти значительно выше минимумов OWASP. Предлагаемая политика:

| Параметр | Значение | Обоснование |
|---|---|---|
| Вариант | Argon2id, версия 0x13 | RFC 9106 |
| Абсолютный минимум (отказ создавать/открывать ниже) | `m = 64 MiB, t = 3, p = 4` | = SECOND RECOMMENDED RFC 9106; выше всех минимумов OWASP |
| Целевой профиль по умолчанию | `m = 256 MiB, t = 3, p = 4` — **калибруется** | цель: время разблокировки 0.5–1.5 с на целевом ПК |
| Профиль «максимальный» (опция) | `m = 1–2 GiB, t = 1–2, p = 4` | приближение к FIRST RECOMMENDED RFC 9106 |
| Соль | 16 байт (128 бит) случайных из CSPRNG, уникальна для каждого хранилища и каждой смены пароля | RFC 9106 §3.1: «16 bytes is RECOMMENDED» |
| Длина выхода | 32 байта (256 бит) | RFC 9106 §4 рекомендует 256-битный тег в обоих вариантах |
| Верхние пределы при чтении | `m ≤ 4 GiB`, `t ≤ 16`, `p ≤ 16` | защита от DoS через подменённый заголовок (zero-trust) |

**Калибровка.** При создании хранилища выполняется бенчмарк (с фиксированным `p=4`, `t=3`, растущим `m`),
выбирается наибольший `m` из списка {64, 128, 256, 512, 1024} MiB, при котором время ≤ целевого,
но не ниже минимума. Параметры записываются в заголовок хранилища. Числа целевого профиля в этом
документе — **гипотеза**, измерения на Windows 11 ПК ещё не проводились (среда подготовки — Linux-контейнер).

### 1.3. Почему XChaCha20-Poly1305, а не AES-256-GCM

| Критерий | XChaCha20-Poly1305 | AES-256-GCM |
|---|---|---|
| Размер nonce | 192 бит — случайный nonce безопасен без счётчиков | 96 бит — при случайных IV NIST SP 800-38D ограничивает число шифрований одним ключом 2^32 |
| Постоянное время без аппаратной поддержки | Да (ARX-конструкция) | Требует AES-NI/CLMUL для безопасной и быстрой реализации |
| Устойчивость к повтору nonce | Повтор катастрофичен для обоих; 192 бита делают случайную коллизию пренебрежимой | Повтор раскрывает ключ аутентификации GHASH |
| Аудит Rust-реализации | `chacha20poly1305`: «one security audit by NCC Group, with no significant findings» (README RustCrypto/AEADs) | `aes-gcm`: тот же аудит NCC Group (RustCrypto, 2020) — проверить по первоисточнику при необходимости |
| Стандартизация | RFC 8439 (ChaCha20-Poly1305); XChaCha — IETF draft, не NIST | NIST SP 800-38D (FIPS-совместимо) |

Решение: **XChaCha20-Poly1305** — основной AEAD. Главный довод — случайные 192-битные nonce
снимают класс ошибок управления nonce (а в хранилище много независимых записей, перезаписываемых
многократно, и ведение глобального счётчика ненадёжно при восстановлении из бэкапа).
Известный компромисс: XChaCha20 не одобрен NIST — для личного менеджера паролей это не является
требованием. Если потребуется FIPS-совместимость, формат допускает идентификатор алгоритма
(`aead_alg`), позволяющий ввести AES-256-GCM-SIV/GCM без смены архитектуры.

Ограничение из README crate: реализация не предназначена для процессоров с переменным временем умножения
(не относится к x86-64/ARM64 Windows 11 ПК).

## 2. Иерархия ключей

```
Master Password (UTF-8, нормализация NFC)
        │
        ▼  Argon2id(password, salt_kdf[16], m,t,p) → 32 байта
   ┌──────────┐
   │   MUK    │  Master Unlock Key — живёт только во время unlock/смены пароля
   └────┬─────┘
        ▼  HKDF-SHA256(ikm=MUK, salt=vault_id, info="VELFORT/v1/kek")
   ┌──────────┐
   │   KEK    │  Key Encryption Key — 32 байта, не хранится
   └────┬─────┘
        ▼  XChaCha20-Poly1305 unwrap (nonce_wrap[24], AAD = canonical(header))
   ┌──────────┐
   │   DEK    │  Vault Root Key — 32 случайных байта, генерируется ОДИН раз при создании
   └────┬─────┘  хранится только в обёрнутом виде (wrapped_dek)
        ├── HKDF(info="VELFORT/v1/items")        → K_items        (записи, папки, история)
        ├── HKDF(info="VELFORT/v1/attachments")  → K_attach       (вложения, этап 5)
        ├── HKDF(info="VELFORT/v1/manifest")     → K_manifest     (целостность набора записей)
        └── HKDF(info="VELFORT/v1/settings")     → K_settings     (настройки безопасности хранилища)
```

Почему так:

* **DEK отделён от пароля** → смена Master Password = только переобёртка DEK (ТЗ 4.2), без перешифровки записей.
* **HKDF между Argon2id и KEK** — domain separation и точка расширения: в будущем во вход HKDF можно
  добавить второй фактор (Secret Key / key file, аналог 2SKD в 1Password) без изменения остальной иерархии.
  *Это вопрос на согласование, см. §8.*
* **Подключи из DEK** — один ключ на один класс данных; компрометация реализации одного класса
  (например, ошибка в шифровании вложений) не даёт ключевого материала другим.

## 3. Форматы шифротекстов

### 3.1. Конверт записи (envelope)

```
envelope = version(1 байт = 0x01) || aead_alg(1 байт = 0x01: XChaCha20-Poly1305)
        || nonce(24 байта, случайный) || ciphertext||tag(16 байт)
```

Открытый текст перед шифрованием: `serialize(payload)` → **дополнение (padding) до кратного 256 байтам**
(схема: длина u32 LE || данные || нули), чтобы уменьшить утечку длины секретов.

### 3.2. AAD — привязка к контексту

```
AAD = "VELFORT" || format_version(u16) || vault_id(16) || record_kind(u8)
    || record_id(16) || revision(u64)
```

Следствия:

* Шифротекст записи нельзя незаметно перенести в другую строку, другое хранилище, другой тип
  (запись ↔ история ↔ папка) или подменить на старую ревизию этой же строки, если ревизия
  хранится и проверяется вне шифротекста (столбец `revision` + манифест, §5).
* Любое изменение бита шифротекста, nonce или AAD → ошибка аутентификации → запись помечается
  повреждённой, данные не возвращаются частично.

### 3.3. Обёртка DEK

`wrapped_dek = XChaCha20-Poly1305(KEK, nonce_wrap, DEK, AAD = canonical(header))`, где
`canonical(header)` — фиксированная бинарная сериализация **всех** открытых полей заголовка:
magic, format_version, vault_id, kdf_alg, m, t, p, salt_kdf, aead_alg, created_at_header.
Подмена любого параметра (например, понижение `m`) → DEK не разворачивается.

## 4. Разблокировка (unlock)

1. Rust читает заголовок `vault_header` (единственная строка). Валидация: magic, поддерживаемая
   `format_version`, допустимые алгоритмы, параметры KDF в пределах [минимум, верхний предел], длины полей.
   Ошибка → «файл не является хранилищем VELFORT или повреждён» (без деталей, в лог — только код ошибки).
2. Пароль поступает из WebView через IPC команду `vault_unlock` один раз; в Rust сразу помещается в
   `SecretString`/`Zeroizing<Vec<u8>>`, нормализуется в NFC.
3. `MUK = Argon2id(...)` в отдельном потоке (UI не блокируется); буфер пароля затирается.
4. `KEK = HKDF(MUK)`; MUK затирается.
5. Попытка `unwrap(wrapped_dek)`. Ошибка AEAD → ответ `InvalidCredentials` (единый ответ для
   «неверный пароль» и «подменён заголовок» — различить их криптографически невозможно и не нужно).
   KEK затирается.
6. Из DEK выводятся подключи; DEK и подключи хранятся в `VaultSession` в защищённом контейнере (§7).
7. Проверка манифеста (§5): расшифровка, сверка с таблицей записей. Расхождение → хранилище открывается
   **только для чтения** с явным предупреждением о целостности.
8. Расшифровываются **только сводки** записей (заголовок, тип, папка, избранное, иконка, домен) для списка и
   поиска. Полные секреты (пароли, номера карт, ключи) расшифровываются по запросу конкретной записи.

Задержка после неудачных попыток (1, 2, 4, … до 30 с) — **только UX-мера** против случайного перебора
за клавиатурой; против атакующего с копией файла защищает исключительно стоимость Argon2id.

## 5. Манифест целостности

Проблема: AEAD защищает каждую запись, но атакующий с правом записи в файл может **удалить строку**
или **откатить одну строку** на её старую копию (вместе со старым `revision`).

Решение: зашифрованный под `K_manifest` объект, обновляемый в той же SQLite-транзакции, что и изменение:

```
manifest = { vault_id, generation(u64, монотонный), entries: sorted[(record_kind, record_id, revision)] }
```

* Проверка при unlock: каждая запись в БД ↔ запись в манифесте; лишние/отсутствующие/несовпадающие
  ревизии → предупреждение о целостности.
* **Остаточный риск:** откат **всего** файла на старую согласованную копию (старый манифест + старые записи)
  обнаружить без внешнего хранилища состояния нельзя. Частичная мера: `generation` последнего успешного
  открытия сохраняется в локальной конфигурации приложения, защищённой DPAPI; откат на меньшее значение →
  предупреждение. Эта мера обходится атакующим, контролирующим и профиль пользователя (см. THREAT_MODEL T-06).

## 6. Смена Master Password

1. Пользователь вводит текущий пароль (повторная аутентификация даже при открытом хранилище) и новый
   (с проверкой силы, см. генератор/zxcvbn-подобная оценка — выбор библиотеки на этапе 2).
2. Повторная проверка текущего пароля через полный путь Argon2id → unwrap (DEK в сессии не используется как
   доказательство знания пароля).
3. Новая соль 16 байт, **перекалибровка параметров KDF**, новый `nonce_wrap`.
4. `wrapped_dek' = wrap(KEK', DEK, AAD = canonical(header'))`.
5. Запись нового заголовка — **одной SQLite-транзакцией** (`BEGIN IMMEDIATE … COMMIT`, `synchronous=FULL`).
   Сбой питания до COMMIT → действует старый пароль; после — новый. Промежуточного состояния нет.
6. Проверочный unwrap нового заголовка перед ответом «успешно».

Важные следствия, которые показываются пользователю:

* **Старые резервные копии** по-прежнему открываются **старым** паролем (они содержат старый `wrapped_dek`).
* Если старый пароль считается скомпрометированным **и** атакующий мог получить копию файла, переобёртки
  недостаточно — DEK уже мог быть раскрыт. Для этого случая предусмотрена отдельная операция
  **«Полная смена ключа» (rekey)**: новый DEK, перешифровка всех записей и истории в одной транзакции
  (с предварительным автоматическим бэкапом).

## 7. Защита памяти

| Мера | Реализация | Ограничение |
|---|---|---|
| Затирание буферов | `zeroize`/`Zeroizing`, `secrecy::SecretBox` для ключей и паролей; `Drop` затирает | Rust может копировать значения при перемещениях; затирается только «последняя» копия — минимизируется отказом от `Clone` и передачей по ссылке |
| Запрет на выгрузку в pagefile | `VirtualLock` для страниц с DEK/подключами | По документации MS: страницы не пишутся в pagefile **пока заблокированы**; лимит числа блокируемых страниц «intentionally small»; гибернация и аварийные дампы документацией не покрыты |
| Шифрование ключей «в покое» в RAM | Опционально `CryptProtectMemory(SAME_PROCESS)` для DEK между операциями | Снижает риск попадания открытого ключа в дамп/своп, но ключ в открытом виде присутствует во время операций; MS прямо указывает, что данные во время использования находятся в памяти открытыми |
| Время жизни секретов | Полные секреты расшифровываются на одну операцию и сразу затираются; в сессии хранятся только сводки | Сводки (заголовки, домены) находятся в памяти, пока хранилище открыто |
| WebView | Значения пароля в JS появляются только при «показать» и удаляются из состояния через N секунд | **Строки JavaScript неизменяемы и управляются GC; гарантированное затирание невозможно** |
| Логи и паника | Собственный `Debug`, печатающий `[REDACTED]`; `panic = "abort"` в release; без crash-reporter'ов | Дамп процесса средствами ОС (WER) может включать память — рекомендуется отключение WER LocalDumps для процесса (исследовать) |

VELFORT **не обещает** абсолютной защиты памяти: процесс с правами пользователя или администратора может
прочитать память открытого хранилища (THREAT_MODEL T-10).

## 8. Вопросы на согласование (криптография)

1. Добавлять ли второй фактор разблокировки — **Secret Key / key file** (высокоэнтропийный 128-битный
   ключ, хранящийся отдельно от файла хранилища) — как опцию или обязательно?
2. Разблокировка через **Windows Hello** (DEK, дополнительно обёрнутый ключом из TPM/Windows Hello) —
   удобно, но расширяет поверхность атаки; предлагается не раньше этапа 5 и только после отдельного анализа.
3. Резервная копия: шифровать **тем же Master Password** (бэкап содержит wrapped DEK — предложено по
   умолчанию) или **отдельным паролем бэкапа**?
4. Целевое время разблокировки (предложено 0.5–1.5 с) и минимальный профиль для слабых ПК.
