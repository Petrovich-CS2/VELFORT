# VELFORT — Cryptography

Статус: **ревизия 2 (после ARCHITECTURE_REVIEW.md), ожидает утверждения**. Параметры, помеченные
«калибруется», фиксируются только после измерений на Windows 11 (Phase 0.5, W1).

Базовые правила:

* Никакой собственной криптографии: только примитивы RustCrypto.
* Все криптографические операции выполняются в Rust-процессе VELFORT. WebView не получает ключей и не шифрует.
* Каждый шифротекст — AEAD и привязан к контексту через AAD (§4).
* Master Password в v1 **вводится в WebView** и передаётся в Rust через IPC (§8.1) — это осознанное ограничение.

## 1. Примитивы

| Назначение | Примитив | Rust crate (версия на 2026-11-25) |
|---|---|---|
| Выработка ключа из пароля | **Argon2id** v0x13 (RFC 9106) | `argon2` 0.6.0 |
| AEAD для записей и обёртки ключей | **XChaCha20-Poly1305** (nonce 192 бит) | `chacha20poly1305` 0.11.0 |
| Потоковое AEAD (бэкапы, вложения) | **STREAM** (Hoang–Reyhanitabar–Rogaway–Vizár, eprint 2015/189), вариант `StreamBE32` | `aead-stream` 0.6.0 |
| Разделение ключей | **HKDF-SHA-256** (RFC 5869) | `hkdf` 0.13.0, `sha2` |
| MAC локального состояния | HMAC-SHA-256 | `hmac` |
| Случайность | CSPRNG ОС | `getrandom` 0.4.3 / `rand` 0.10.4 |
| Очистка памяти | `zeroize`, `secrecy` | `zeroize` 1.9.2, `secrecy` 0.10.3 |
| Сравнение в постоянном времени | `subtle` | `subtle` 2.6.1 |

Версии получены через crates.io API; исходники `aead` 0.6.1, `aead-stream` 0.6.0, `chacha20poly1305` 0.11.0
скачаны и просмотрены (см. ARCHITECTURE_REVIEW §0, S4–S6).

### 1.1. Почему Argon2id

RFC 9106 §1: «Argon2id MUST be supported by any implementation of this document». OWASP рекомендует
Argon2id первым выбором. Быстрые хеши (SHA-256) для выработки ключа из пароля не используются.

### 1.2. Параметры Argon2id

* OWASP минимумы: `46 MiB/t=1/p=1`, `19 MiB/t=2/p=1`, `12 MiB/t=3/p=1`, `9 MiB/t=4/p=1`, `7 MiB/t=5/p=1`.
* RFC 9106 §4: FIRST RECOMMENDED `t=1, p=4, 2 GiB`; SECOND RECOMMENDED `t=3, p=4, 64 MiB`; соль 128 бит; тег 256 бит.

| Параметр | Значение |
|---|---|
| Минимум (ниже — отказ создавать/открывать) | `m=64 MiB, t=3, p=4` (= SECOND RECOMMENDED) |
| По умолчанию | `m=256 MiB, t=3, p=4` — **гипотеза, калибруется (W1)**; цель 0.5–1.5 с |
| Максимальный профиль (опция) | `m=1–2 GiB, t=1–2, p=4` |
| Соль | 16 байт CSPRNG; новая при создании, при каждой смене пароля, для каждого бэкапа |
| Выход | 32 байта |
| Верхние пределы при чтении | `m ≤ 4 GiB, t ≤ 16, p ≤ 16` (защита от DoS подменённым заголовком) |

### 1.3. Почему XChaCha20-Poly1305

* 192-битный nonce допускает **случайную генерацию без состояния** (§3). Для AES-GCM с 96-битным случайным IV
  NIST SP 800-38D ограничивает число шифрований одним ключом 2^32 (то же предупреждение — в документации
  `aead` 0.6.1, `src/lib.rs`).
* Постоянное время в программной реализации; аудит NCC Group для `chacha20poly1305` (README crate).
* Компромисс: XChaCha20 не одобрен NIST. Поле `aead_alg` в формате оставляет возможность смены алгоритма.

## 2. Иерархия ключей и обоснование каждого звена

```
Master Password ──NFC──► Argon2id(pw, salt_vault, m,t,p) ──► MUK (32 B, эфемерный)
                                                             │
          HKDF-Extract(salt = vault_id, IKM = MUK) → PRK     │
          HKDF-Expand(PRK, info = "VELFORT/v1/kek") ◄────────┘
                                │
                               KEK (32 B, эфемерный)
                                │  XChaCha20-Poly1305 unwrap, AAD = purpose HEADER_WRAP || canonical(header)
                               DEK (32 B, случайный, создаётся один раз; меняется только при rekey)
                                │  HKDF-Expand(PRK = DEK, info = …)  (Extract пропущен, RFC 5869 §3.3)
     ┌──────────────┬───────────┼──────────────┬──────────────┬────────────────┐
  K_items       K_attach    K_manifest     K_settings      K_local
  (записи,      (вложения)  (манифест)     (настройки      (MAC локального
  папки,                                   хранилища)      состояния, §5.3)
  история)
```

| Звено | Зачем нужно | Что будет без него |
|---|---|---|
| **NFC-нормализация** | Один и тот же пароль, введённый разными методами ввода (составные/предсоставленные символы), даёт одни байты | Пользователь не сможет открыть хранилище с другой раскладки/IME |
| **Argon2id** | Замедление и удорожание (по памяти) offline-перебора | Перебор пароля со скоростью быстрых хешей |
| **HKDF после Argon2id** | (1) Domain separation: MUK используется только для KEK; (2) точка расширения: при добавлении Secret Key/key file IKM станет `MUK ‖ SK` — тогда HKDF-Extract **обязателен** для корректного объединения; (3) vault_id как salt привязывает KEK к хранилищу | Строго для безопасности v1 **не обязательно** (выход Argon2id уже 256-битный псевдослучайный ключ). Оставлено, т.к. стоимость пренебрежима, а расширение без него потребует смены формата |
| **KEK ≠ DEK** | Смена пароля = переобёртка 48 байт без перешифровки записей; несколько обёрток одного DEK в будущем (Windows Hello, Secret Key) | Смена пароля требует перешифровки всего хранилища |
| **Подключи из DEK** | Один ключ — один класс данных; независимость (ниже) | Ошибка в одном классе (например, вложения) затрагивает ключ всех данных |

### 2.1. Разделение и независимость ключей

* Подключи выводятся `HKDF-Expand(DEK, info)` с уникальными `info`: `"VELFORT/v1/items"`, `"VELFORT/v1/attach"`,
  `"VELFORT/v1/manifest"`, `"VELFORT/v1/settings"`, `"VELFORT/v1/local-state"`. RFC 5869 §3.3 допускает пропуск
  Extract, когда IKM уже является криптографически стойким ключом (DEK — 32 байта CSPRNG); §3.2: `info` служит
  для привязки выведенного материала к контексту.
* При стандартном допущении, что HMAC-SHA-256 — PRF, выходы с разными `info` вычислительно независимы;
  знание одного подключа не даёт ни DEK, ни других подключей.
* В коде подключи — **разные типы** (`ItemsKey`, `ManifestKey`, …), функции шифрования принимают только свой тип —
  перепутать ключ на уровне компиляции невозможно.

### 2.2. Уникальность соли

* `salt_vault` — 16 байт CSPRNG, генерируется заново при создании хранилища и **при каждой смене пароля**.
* Бэкап использует **свою** соль `salt_backup` (§7). Соли никогда не берутся из входных данных.
* Вероятность совпадения двух случайных 128-битных солей среди 2^32 значений ≤ 2^63/2^128 = 2^-65.
* Дополнительно vault_id/backup_id (16 байт CSPRNG) входят в HKDF salt — даже при совпадении соли KEK различны.

## 3. Nonce

### 3.1. Генерация и хранение

* Каждый вызов AEAD-шифрования записи: новый 24-байтовый nonce из `getrandom` **внутри** функции `crypto::seal`.
  API не принимает nonce извне (SR-ENC-2).
* Nonce хранится открыто в начале envelope (§4.1). Секретности nonce не требует.
* Ошибка `getrandom` → операция прерывается с ошибкой; **никакого fallback-генератора**.
* Потоковое шифрование: `StreamBE32` строит nonce как `prefix(19 B, случайный) ‖ counter(u32 BE) ‖ last_flag(1 B)`
  (исходник `aead-stream` 0.6.0, `aead_nonce`). Каждый поток — **с собственным случайным ключом** (§7), поэтому
  повтор prefix между потоками не приводит к повтору пары (ключ, nonce).

### 3.2. Оценка вероятности повтора

Для q случайных 192-битных nonce под одним ключом вероятность хотя бы одного совпадения
≤ q(q−1)/2 / 2^192 (оценка «дней рождения»). Расчёт (Python, `log2`):

| q (шифрований одним ключом) | Верхняя граница вероятности |
|---|---|
| 2^20 (~10^6) | 2^-153 |
| 2^32 (~4·10^9) | 2^-129 |
| 2^40 (~10^12) | 2^-113 |

Реалистичный объём для менеджера паролей — менее 2^20 шифрований за всю жизнь хранилища.

### 3.3. Поведение в нештатных ситуациях

| Ситуация | Почему повтора nonce нет |
|---|---|
| Аварийное завершение посреди записи | Состояния nonce нет; транзакция SQLite откатывается; повторная попытка генерирует новый nonce |
| Восстановление базы из бэкапа / отката | Именно поэтому выбраны случайные, а не счётные nonce: счётчик после отката повторил бы значения, случайный генератор — нет |
| Повторное шифрование записи (правка, rekey, миграция) | Каждое шифрование — новый nonce, даже для идентичного открытого текста |
| Смена пароля | Новый KEK (новая соль) и новый `wrap_nonce` |
| Клонирование ВМ со снимком памяти | Если ОС восстановит одинаковое состояние CSPRNG в двух клонах, возможны одинаковые nonce в обоих клонах. Это проблема уровня ОС/гипервизора; **остаточный риск**, задокументирован |

## 4. AAD — привязка шифротекста к контексту

### 4.1. Envelope

```
envelope = version(1 B = 0x01) ‖ aead_alg(1 B = 0x01) ‖ nonce(24 B) ‖ ciphertext ‖ tag(16 B)
plaintext = len(u32 LE) ‖ CBOR/JSON(payload) ‖ zero padding до кратного 256 байтам
```

### 4.2. Состав AAD

```
AAD = "VELFORT\0"            (8 B, domain tag)
    ‖ format_version   u16
    ‖ vault_id         16 B
    ‖ purpose          u8   ← назначение шифротекста (новое в ревизии 2)
    ‖ record_id        16 B (для singleton-объектов — нули)
    ‖ revision         u64
    ‖ extra            переменная часть по purpose (длина-префикс)
```

| `purpose` | Значение | `extra` |
|---|---|---|
| 0x01 HEADER_WRAP | обёртка DEK | `canonical(header)` |
| 0x10 ITEM_SUMMARY | `items.summary` | — |
| 0x11 ITEM_PAYLOAD | `items.payload` | — |
| 0x12 ITEM_HISTORY | `item_history.payload` | — |
| 0x20 FOLDER | `folders.data` | — |
| 0x30 SETTINGS | `vault_settings.data` | — |
| 0x40 MANIFEST | `manifest.data` | `generation` |
| 0x50 ATTACH_META | `attachments.meta` | `item_id` |
| 0x51 ATTACH_CHUNK | сегменты вложения (STREAM) | `attachment_id` |

**Тип элемента** (Login, Card, …) зашифрован и потому не входит в AAD; он находится в аутентифицированном
открытом тексте **и** summary, **и** payload. После расшифровки обязательна проверка
`summary.kind == payload.kind && summary.schema` допустима — иначе запись помечается повреждённой.

**Назначение поля.** Поля записи шифруются одним blob'ом `payload`; назначение каждого поля задаётся
структурой сериализации внутри аутентифицированного открытого текста (имена/теги полей). Перестановка
полей внутри blob'а без ключа невозможна (AEAD). Если в будущем отдельное поле получит собственный blob,
для него вводится отдельный `purpose`.

### 4.3. Предотвращаемые атаки

| Атака (атакующий с правом записи в файл, без ключа) | Что её останавливает |
|---|---|
| Перенос шифротекста из другого хранилища VELFORT | `vault_id` в AAD (и другой ключ) |
| Перестановка blob'ов между записями | `record_id` |
| Перестановка `summary` ↔ `payload` одной записи (дефект D1 ревизии 1) | `purpose` |
| Подстановка версии из истории в текущую запись | `purpose` (HISTORY ≠ PAYLOAD) |
| Подстановка старой ревизии записи с исправленным столбцом `revision` | AAD проходит, **но** манифест хранит актуальную ревизию → обнаружение (§5) |
| Подмена параметров KDF/алгоритмов в заголовке (downgrade) | `canonical(header)` в AAD обёртки DEK |
| Подстановка данных, зашифрованных под другой версией формата | `format_version` |
| Перестановка/усечение/дублирование сегментов потока | счётчик и флаг last в nonce STREAM + `extra` |

## 5. Манифест целостности

```
manifest (purpose MANIFEST, K_manifest) = {
  vault_id, generation: u64 (монотонно +1 при каждой записи),
  header_hash: SHA-256(canonical(header)),
  entries: sorted[(purpose, record_id, revision)]   // items, history, folders, settings, attachments
}
```

Обновляется **в той же SQLite-транзакции**, что и любое изменение. Проверяется при каждой разблокировке.

### 5.1. Что обнаруживается

| Атака | Обнаружение | Механизм |
|---|---|---|
| Удаление записи (строки) | **Да** | запись есть в манифесте, нет в БД |
| Добавление строки (например, удалённой записи из старой копии) | **Да** | строки нет в манифесте |
| Подмена содержимого записи | **Да** | ошибка AEAD |
| Перестановка записей | **Да** | `record_id`/`purpose` в AAD |
| Откат отдельной записи на старую ревизию | **Да** | ревизия ≠ ревизии в манифесте |
| Подделка манифеста | **Да** | ошибка AEAD (K_manifest) |
| Подстановка старого манифеста при текущих записях | **Да**, если после него была хотя бы одна запись | расхождение entries |
| Откат заголовка (например, к старому паролю) | **Да**, после разблокировки | `header_hash` |
| Откат **всей** базы на старое согласованное состояние | **Нет** (см. §5.2) | — |

### 5.2. Фундаментальное ограничение: полный откат

Старая копия файла — это полностью корректное, аутентичное состояние: все AEAD-теги, манифест и заголовок
согласованы между собой. **Обнаружить подмену текущего файла его же более ранней версией, используя только
содержимое файла, невозможно** — для этого нужно доверенное внешнее состояние (монотонный счётчик в
доверенном хранилище, TPM NV-counter, удалённый сервис). В архитектуре v1 такого доверенного состояния нет.

### 5.3. Частичная мера: локальное состояние

* В `%APPDATA%\VELFORT\config.json` хранится `{vault_id, last_seen_generation, mac}`,
  `mac = HMAC-SHA-256(K_local, vault_id ‖ generation)`.
* При разблокировке: `generation < last_seen_generation` → предупреждение «хранилище старее, чем при прошлом
  открытии на этом компьютере» (открытие с выбором пользователя).
* Защищает от атакующего, который может изменить **только файл хранилища** (облачная папка, USB-носитель).
* **Не защищает**: от атакующего, который может также вернуть старый `config.json` (тот же пользователь ОС);
  при первом открытии на другом компьютере; после удаления конфигурации.

## 6. Смена ключевого материала

### 6.1. Смена Master Password

1. Повторный ввод текущего пароля и полный путь Argon2id → unwrap (DEK из сессии **не** считается
   доказательством знания пароля).
2. Новая `salt_vault` (16 B), перекалибровка параметров KDF, новый `wrap_nonce`, новый KEK.
3. `wrapped_dek' = seal(KEK', DEK, AAD = HEADER_WRAP ‖ canonical(header'))`.
4. В **одной** транзакции (`BEGIN IMMEDIATE … COMMIT`, `synchronous=FULL`): новый заголовок + манифест
   с новым `header_hash` и `generation+1`.
5. Контрольный unwrap нового заголовка до сообщения «успешно».

Корректность: записи не перешифровываются (DEK тот же); сбой до COMMIT — действует старый пароль, после — новый.
Следствия для пользователя: старые бэкапы открываются **старым** паролем; переобёртка не защищает, если атакующий
уже получил DEK (из старой копии файла и старого пароля).

### 6.2. Полная смена ключа (rekey) при подозрении на компрометацию DEK

1. Повторная аутентификация; создание защитной копии файла.
2. Новый DEK (CSPRNG) → новые подключи; новый заголовок (новая соль, новый KEK).
3. Перешифровка **всех** объектов (items: summary+payload, history, folders, settings, attachments, manifest) с
   новыми nonce, в одной транзакции.
4. `VACUUM` (удаление старых страниц из файла; в режиме `journal_mode=DELETE` журнал удаляется после COMMIT).
5. Контрольная расшифровка всех объектов новым ключом.

Ограничения rekey (показываются пользователю):

* Старые бэкапы, копии файла и остатки на ФС/SSD остаются зашифрованными **старым** DEK.
* Rekey восстанавливает конфиденциальность **будущих** данных, но **не целостность**: обладатель старого DEK мог
  создать поддельные, но корректно аутентифицированные записи. При подозрении на компрометацию рекомендуется
  восстановление из бэкапа, созданного до инцидента (бэкап защищён отдельным ключом от пароля, §7), и смена паролей
  сервисов.

## 7. Резервные копии (`.velfort-backup`)

Требования владельца: Master Password, отдельная соль и независимый ключевой контекст, AEAD, проверка целостности,
атомарное восстановление, без временных расшифрованных файлов.

### 7.1. Ключи бэкапа

```
salt_backup (16 B, CSPRNG), backup_id (16 B, CSPRNG)
MUK_b = Argon2id(Master Password, salt_backup, m,t,p)          // требуется повторный ввод пароля
KEK_b = HKDF(salt = backup_id, IKM = MUK_b, info = "VELFORT/v1/backup-kek")
BK    = 32 B CSPRNG                                             // ключ содержимого, уникален для бэкапа
wrapped_bk = seal(KEK_b, BK, AAD = "VELFORT-BACKUP\0" ‖ canonical(backup_header))
```

Ключевой контекст бэкапа не зависит от DEK и от `salt_vault`.

### 7.2. Содержимое и формат

```
file = magic "VELFORT-BACKUP\0" ‖ backup_format u16 ‖ header_len u32 ‖ backup_header ‖ stream_segments…
backup_header = { backup_format, backup_id, created_at, source_format_version, source_vault_id,
                  kdf_alg, m, t, p, salt_backup, wrap_nonce, wrapped_bk, stream_nonce_prefix(19 B),
                  segment_size = 1 MiB }
segments = EncryptorBE32<XChaCha20Poly1305>(BK, stream_nonce_prefix),
           AAD каждого сегмента = SHA-256(canonical(backup_header))
plaintext потока = Connection::serialize(main)  // снимок БД в памяти (rusqlite feature `serialize`)
```

* Снимок делается в памяти, **без временного файла**. Сам снимок по-прежнему содержит записи, зашифрованные DEK
  (внутренний слой) — двойная защита.
* Буфер снимка затирается после шифрования.

### 7.3. Потоковое шифрование — проверено по исходникам

* `aead` 0.6.1: модуля `stream` **нет**; документация crate ссылается на отдельный `aead-stream`.
* `aead-stream` 0.6.0 (RustCrypto/AEADs): `EncryptorBE32`/`DecryptorBE32`, `StreamBE32` — 32-битный BE-счётчик +
  1 байт флага last в последних 5 байтах nonce; максимальное значение счётчика запрещено, чтобы оставался
  последний сегмент. При nonce 24 байта prefix = 19 байт. Предел: < 2^32 сегментов (при 1 MiB — более 4 PiB).
* Внешний аудит `aead-stream` в изученных источниках **не найден** → тесты: перестановка, усечение, дублирование,
  удаление последнего сегмента, данные после последнего сегмента, изменение заголовка.

### 7.4. Проверка и восстановление

1. Разбор заголовка с лимитами; неизвестный `backup_format` → отказ.
2. Ввод пароля → `KEK_b` → unwrap `BK` (ошибка → «неверный пароль или повреждённый бэкап»).
3. Расшифровка всех сегментов в память; последний сегмент обязан иметь флаг last; лишние байты → отказ.
4. `deserialize` в in-memory соединение; `PRAGMA integrity_check`; проверка `application_id`, заголовка хранилища;
   разблокировка снимка тем же паролем; проверка манифеста.
5. Только после успеха всех шагов — запись: временный файл в **целевом каталоге** (`<name>.velfort.restore-<rand>`) →
   `FlushFileBuffers` → `MoveFileExW(…, MOVEFILE_WRITE_THROUGH)` **без** `MOVEFILE_REPLACE_EXISTING`.
6. Восстановление в v1 — только в **новый** файл; существующее хранилище не перезаписывается.
7. Осиротевшие `*.restore-*` удаляются при следующем запуске. Они содержат только БД с полевым шифрованием
   (открытых секретов нет), но не являются валидным хранилищем.

Атомарность: Microsoft не заявляет атомарность `MoveFileExW`/`ReplaceFileW` (ARCHITECTURE_REVIEW S13). Схема
«полностью записанный новый файл + rename без замены» гарантирует, что **существующие** файлы не повреждаются
при любом исходе; поведение при сбое проверяется в Phase 0.5 (W12).

### 7.5. Защитная копия перед миграцией/rekey

Не требует пароля: копия файла `.velfort` (через `serialize` → новый файл по схеме §7.4 п.5). Файл и так зашифрован
на уровне полей. Это не `.velfort-backup` и не заменяет пользовательские бэкапы.

## 8. Разблокировка и защита памяти

### 8.1. Путь Master Password (v1)

```
<input type=password> (WebView2 renderer process, JS-строка)
   └─ submit: value читается один раз → input.value = '' → invoke('vault_unlock')
        └─ IPC Tauri/WebView2 (буферы вне контроля zeroize)
             └─ Rust: немедленно в Zeroizing<Vec<u8>> → NFC → Argon2id → затирание
```

Пароль **существует в JavaScript** до сборки мусора; гарантированное затирание невозможно. Альтернативы
(системный диалог, нативный компонент) проанализированы в ARCHITECTURE_REVIEW §3.1.

### 8.2. Шаги разблокировки

1. Валидация заголовка (magic, версия, алгоритмы, диапазоны KDF, длины). Ошибка → единый ответ.
2. Argon2id в отдельном потоке → HKDF → KEK → unwrap DEK. Ошибка AEAD → `InvalidCredentials` (неверный пароль
   и подменённый заголовок неразличимы).
3. Вывод подключей; MUK/KEK/пароль затираются.
4. Проверка манифеста (§5) и локального состояния (§5.3).
5. Расшифровка только сводок; payload — по требованию.

UI-задержка после неудач (1, 2, 4 … 30 с) — только против перебора за клавиатурой.

### 8.3. Память

| Мера | Ограничение |
|---|---|
| `zeroize`/`secrecy`, без `Clone`, `Debug` = `[REDACTED]` | Копии при перемещениях/реаллокации и в чужих буферах (IPC, serde) не затираются |
| `VirtualLock` для страниц с ключами | Документация MS: не пишутся в pagefile, **пока заблокированы**; лимит «intentionally small»; гибернация не упомянута. Проверка W2 |
| `CryptProtectMemory(SAME_PROCESS)` для DEK между операциями (опционально) | Во время операции ключ открыт. Проверка W3 |
| Сводки в памяти, payload — на одну операцию | Сводки открыты весь сеанс |
| WebView: секреты только по reveal, перезагрузка документа при блокировке | Строки JS не затираются |
| `panic = "abort"`, без crash-reporter'ов | Дамп ОС (WER) может содержать память — проверка W13 |

VELFORT **не обещает** абсолютной защиты памяти.
